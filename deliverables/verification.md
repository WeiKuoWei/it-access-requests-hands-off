# Verification

All automated tests use a **mocked** provider (`FakeClient` in `tests/conftest.py`, scripted per test). They never call the network. Expected values are written by hand from the messages and policy, not read back from extractor output.

## Commands
```
.venv/bin/python -m pytest -q                 # 274 tests, ~55 s, offline; no API key needed (without one, 1 test that scans for your real key is skipped) (the 2,000-document test is ~8 s, the parallel-process tests ~40 s)
.venv/bin/python -m pytest -q tests/test_cli.py        # operator CLI: mock isolation, empty install, retry exit code (6 tests, sandboxed)
.venv/bin/python -m pytest -q tests/test_redaction.py  # credential redaction + repository secret scans (27 tests, <1 s)
.venv/bin/python -m pytest -q tests/test_parallel.py -k reflected   # real CLI process vs a provider that echoes the key (8 runs, ~6 s)
.venv/bin/python -m pytest -q tests/test_policy_cases.py   # withdrawals, corrections, identifier mismatches (135 tests, <1 s)
.venv/bin/python -m pytest -q tests/test_parallel.py   # real simultaneous operator processes, incl. the credential-reflection runs (16 tests, ~45 s)
.venv/bin/python -m pytest -q tests/test_export.py     # snapshot_id / consistent-read checks (10 tests)
.venv/bin/python -m intake check-export                # prove deliverables/extractions.jsonl and queue.json match
.venv/bin/python -m pytest -q tests/test_refresh.py    # settings/policy change, stale detection, refresh, history
.venv/bin/python -m pytest -q -s tests/test_scale.py   # rate limit / slow response / outage / interrupt / 2,000 messages
.venv/bin/python -m intake accuracy           # live-or-mock field comparison vs tests/expected.json
.venv/bin/python -m intake accuracy --expected tests/policy_probe_expected.json     # same, for the 11-message fresh-wording probe (see accuracy.md)
.venv/bin/python -m intake accuracy --expected tests/policy_holdout_expected.json   # same, for the 8-message held-out set (run against a scratch INTAKE_DB)
.venv/bin/python -m intake --mock intake materials/requests tests/fixtures/IT-101.json   # offline smoke run; uses data/mock/, never the real store or deliverables (use --mock on queue/accuracy too)
```

## Real parallel operators (`tests/test_parallel.py`)
Each operator is a separate OS process running the real CLI (`python -m intake …`, started through `tests/launch.py`, which only adds a start barrier so processes begin within milliseconds of each other). They share one SQLite file and one output directory and call the real `openai` client over real HTTP against a local fake provider (`tests/fake_provider.py`, selected with `OPENAI_BASE_URL`; it counts calls per message). Only the model is faked. Provider results here are **mocked**, not live.

| Scenario | Assertion |
|---|---|
| 4 operators start together on 60 documents | each document is sent to the provider exactly once (60 calls total) and has exactly one owner; collisions really happened (some `skipped-busy`); no operator hit `database is locked`; no dangling claims; `extractions.jsonl` and `queue.json` contain all 60 and agree per document on `attempt_id`, `source_sha256` and status; the recorded hash equals the file's SHA-256 |
| 2 operators with different `OPENAI_MODEL` at once | a document is extracted at most once per configuration, never twice for the same one; every provider call has a kept record attributable to the operator that made it (by PID); `status` under model-b lists exactly the documents whose current result is model-a as stale; `refresh` brings exactly those up to date — one new call each, or none when the other operator had already produced a model-b result for that document (it is reused); the model-a attempts stay in history |
| operator killed with `SIGKILL` mid-run | `queue --json` from another process lists exactly the finished documents as entries and exactly the in-flight ones as `pending`, attributed to the dead operator's PID; after the lease expires a second operator finishes everything; finished documents were not re-sent; in-flight ones were sent at most twice; history keeps one `abandoned` attempt per in-flight document |
| queue read while intake is running | a `queue --json` process during a running intake sees some documents done and others pending (no document in both lists), and does not disturb the running operator |
| 2 operators `retry` after an outage together | 30 documents failed with 503; after recovery every document has exactly one failed and one successful attempt, and the provider saw exactly 2 calls per message (1 failed + 1 successful), not 3 |
| 8 simultaneous `export` processes | all succeed and the deliverables are complete and consistent; no stray temp files |
| slow exporter vs newer work | one exporter takes its snapshot (6 documents) and stalls before writing; another operator completes 3 more documents and exports; the final deliverables contain all 9 |
| readers vs a continuously publishing writer | a writer adds a document and exports 40 times with a 25 ms gap between files; a *naive* reader (two plain reads) sees mixed pairs (the hazard is real and every one is detectable by `snapshot_id`); a `read_consistent` reader with its retry layer disabled, protected only by the shared lock, performs more than 20 reads with **zero** mixed pairs; nobody ever reads a torn file; afterwards `check-export` reports OK with 40 records |

**Export consistency checks, in-process (`tests/test_export.py`):** both files carry one `snapshot_id`; the id is content-derived (same state → same id, new document or changed settings → new id); an empty export is consistent; a mixed pair, one foreign record, or files with no `snapshot_id` are refused with `InconsistentSnapshot`; a reader started while an export is mid-publish waits for it and returns the new complete pair (took >0.4 s, no retry layer); `queue.json` is written last; `check-export` returns 0 for a good export and 1 for no export, an older queue next to newer records, or queue entries that disagree with their records even when the ids match. Mutation check: removing the reader's shared lock makes the lock-only reader see mixed pairs (78 in one run) and fails the cross-process test.

**Defects these tests found (and the repairs):**
1. *Duplicate model calls.* Operators checked "is there a finished result?" and then claimed the document in a separate step; if another operator finished in between, both paid for the same extraction. Fixed by repeating the check inside the claim transaction (`dedupe` / `AlreadyDone`) and making re-route/rollback copies idempotent.
2. *`retry` repeated work.* Two operators retrying the same failure both re-extracted it. Fixed with a guard that claims the document only if its latest result is still the one the operator saw (`expect_current` / `StateChanged`, outcome `already-handled`).
3. *Start-up crash.* Several operators starting at once on a fresh database could fail with `database is locked` while switching SQLite to WAL mode. Fixed by only switching when needed and retrying initialisation.
4. *Stale exports.* Without a lock an operator holding an older snapshot could write last. Fixed with the export lock described below.

**How strongly the tests detect these (mutation checks, run by hand):** disabling the in-transaction check fails the 4-operator and different-model tests; disabling the retry guard fails the retry test; reverting the start-up fix fails both of those start-together tests; disabling the export lock fails the slow-exporter test. Races that are microseconds wide in normal runs are widened for the test only: `tests/launch.py` can insert a random delay before each claim (`LAUNCH_CLAIM_DELAY_MS`) or stall an exporter after its snapshot (`LAUNCH_EXPORT_DELAY_MS`) to imitate a slow disk. Without that widening, the duplicate-call race did not reproduce reliably (it appeared once, on a cold first run), so the tests are only as strong as that injected delay.

## Withdrawals, explicit corrections and identifier mismatches (`tests/test_policy_cases.py`, `intake/finalize.py`)
Policy sentences that can be checked mechanically are enforced in code rather than trusted to the model. `finalize()` runs on every extraction before routing and again, on the stored extraction, when the policy version changes (no model call). It is idempotent and is part of the policy-version hash. Expected routing comes from the policy text; model replies are hand-written (provider **mocked**). The supplied samples IT-005, IT-008, IT-015 and IT-016 are used as written; further wording comes from `tests/fixtures/policy_probe/`.

| Policy rule | Assertions |
|---|---|
| **Identifier mismatch** — keep the stated ID, record the mismatch as an issue | IT-016 (states IT-061): `request_id` stays IT-061, a `mismatch:` issue naming both IDs is added even when the model wrote none, status needs-information / clarify; the issue reaches `extractions.jsonl` and `queue.json`; comparison ignores case and spacing (`it-016` = `IT-016`) but not transposed digits (`IT-061`), missing zero-padding (`IT-16`) or extra digits; running the check twice, or when the model already wrote a mismatch issue, never duplicates it; a null ID is "missing", not a mismatch |
| mismatch vs rule order | a withdrawal with a mismatched ID is still confirm-withdrawal (rule 2 precedes rule 3) with the issue recorded; an override attempt plus a mismatch is inspect-message (rule 1); kind `other` plus a mismatch is clarify with both reasons |
| document identity | two documents stating the same request ID stay two queue entries; a document that states another file's name is flagged, the file it names is not; a mistyped ID that the message itself corrects matches its filename and routes normally |
| **Withdrawal** — request_id + request_date → IT Service Desk, review, confirm-withdrawal; other fields may be null, absent facts identified in issues | IT-005 shape: confirm-withdrawal even though system, environment, permission, purpose and both dates are null; each null gets a `missing:` issue even when the model wrote no issues; a withdrawal that also restates the original details is still confirm-withdrawal; missing request_date, missing request_id, or both → needs-information / clarify with the reason; a withdrawal containing an override goes to inspect-message |
| withdrawal independence | the withdrawal message and the original request are separate documents and separate queue entries, the original is untouched; a request absent from a later batch stays in the queue (absence does not withdraw) |
| **Explicit correction** replaces the earlier value | IT-008 (environment) and IT-015 (dates): correct extractions route as staging/read → System Owner and keep the correction in `supporting_quotes`; fresh wording for permission (write → Security Review), environment (production → Security Review), end date only (start kept), mistyped request ID |
| correction ignored by the model | the model keeps the superseded environment, dates, permission or ID → the value is **not** overwritten, a `correction-ignored:` issue says what the correction asked for, and the document goes to needs-information / clarify so a person looks; a correction that moves a request to production is routed as production when applied |
| correction precision | no false flags on the hand-written gold facts of all 20 supplied messages; an ambiguous correction ("staging for the demo and production for the audit") is never flagged; old-value phrasing ("the old value is production; the new one is staging", "previous environment was production, the right one is staging", "staging, not production", "production rather than staging") resolves to the new value; a correction of the submission date, or a permission word in a correction about something else, is not read as an access correction |
| correction preservation | a correction the model left out of `supporting_quotes` is appended verbatim (an exact substring of the message) with a `note:` issue; one the model already quoted is not added again |
| no correction label, no correction | "Actually I think I might need production instead" is not treated as a correction; it stays an unresolved conflict (environment null) → clarify; a correction to a *relative* date leaves the dates null → clarify |
| unexplained nulls | every null scalar gets an issue that names it; an explanation the model already gave is not duplicated; a `relative-date:` issue that names no field is supplemented |
| policy refresh | a record made before these checks existed picks them up on a policy change as a `rerouted` attempt: no second model call, the earlier version retained unchanged in history, the new one linked to it; `finalize.py` is part of the policy-version hash |
| **Hedged alternative dates** — a tentative alternative next to a stated value is a contradiction (unresolved, not a guess) | a model that keeps the stated dates is flagged `hedged-alternative:` and sent to needs-information / clarify for five phrasings (hedge on the end date, the start date, the whole window, "(or possibly X)", "not sure if the end should really be X"); the values are **not** rewritten and only one issue is added per message; the issue names the floated date and quotes the sentence; a model that already nulled the date and wrote a `conflict:` issue is not flagged again; controls are left alone (a hedge naming no date, an unrelated date in a different sentence, a labelled correction beside a vague hedge, a hedge that only restates the used dates, the request date in a hedged sentence); a hedge inside a labelled correction is left to the correction check (which reports a different issue); idempotent; routing reason added |
| backstop precision / recall | with correct gold extractions for **every** message we hold (20 supplied + probe + first held-out + dev + dev 2), the check flags exactly the hedged-date messages (IT-225 and IT-251–255) and nothing else; none of the supplied messages is flagged |
| **Hedged environment / permission** — same rule, for the fields that decide who reviews the request | a model that keeps `staging` next to "Perhaps production is the better fit", "Thinking about production instead, still undecided" or "I'm not sure whether staging is enough, production may be needed" is flagged and sent to clarify (the extracted value is **not** rewritten); same for "Maybe write? Haven't decided." and "Or perhaps admin" on a write request; without the flag the same extraction routes to System Owner (asserted); a model that already recorded a `conflict:` about that field is not flagged again (with the value still present, so the null rule cannot be the reason), but a conflict about a *different* field does not suppress it; one issue per kind even with several hedged sentences, and environment + permission + dates can each be reported; 7 cue variants ("Wondering whether", "Probably", "Thinking about", "Undecided, but", "I guess", "It depends, maybe", "Considering"); no cue, no flag; a hedge inside a labelled correction is left to the correction check |
| hedged environment / permission: look-alikes | 18 sentence-level cases: real alternatives are returned ("Maybe write instead.", "Maybe write?", "I wonder if I need write access.", "Perhaps admin.", "Maybe read-only would be enough.", "Could be admin rather than write.", "Maybe staging instead of production.", "Maybe read instead of write." with write stated); look-alikes are not ("I might only need read, not write.", "I do not need write, maybe.", "…slow in production but I only need staging.", "I just need staging, perhaps production is slower.", `read`/`write` as verbs, the stated value restated, no concrete alternative); controls IT-286–IT-290 (negation, restriction, verb, restated value, no alternative) are never flagged; recall/precision over dev set 2 flags exactly IT-281–IT-285 and never any supplied message, whatever environment/permission a model keeps |
| **Dropped corrected date** | the failure seen live on IT-015 (new start applied, end nulled with "range: … is not a valid date") is flagged `correction-ignored: the correction names 2026-10-31 but end_date is null` and goes to clarify, values not rewritten; both dates dropped is flagged; not flagged when the model recorded a date conflict, when both dates are filled, when a correction also names the superseded date ("end date is 2026-11-02, not 2026-10-30") and was applied correctly, or when the correction is to relative dates |
| live-check fixtures | every non-null expected value in the probe, first held-out, dev, dev 2 and both sealed (`policy_holdout2`, `policy_holdout3`) expectation files literally appears in its message; each fixture set and its expectations stay in step |

**Mutation checks (run by hand, each caught by the tests):** no mismatch issue recorded; nulls left unexplained; ignored corrections not flagged; correction quote not preserved; mismatch outranking a withdrawal; withdrawal required to carry full details; identifiers compared case-sensitively. For the hedged-date backstop, eight further mutations (backstop not called; hedge cue never matching; hedge cue not required; used dates not excluded; labelled corrections not skipped; an already-recorded conflict flagged again; routing ignoring the flag; the check nulling a date instead of only flagging) were each caught by a named test. The first run of that mutation script was unreliable: one mutation broke the file's indentation and "failed" every test at import, and two others were missed because one mutation only swapped a single cue word and one test was vacuous (it gave the extraction the corrected date, so nothing could be floated either way); the script now checks for collection errors, the mutations were corrected and the vacuous test was fixed before the results above were taken. For the extended backstop and the dropped-correction-date check, fifteen further mutations were each caught by a named test: restriction guard removed; negation guard removed; verb guard removed; the stated value counted as an alternative; an already-recorded conflict flagged again; environment/permission never checked; hedge cue not required; labelled corrections not skipped; the cue list losing `wonder\w*`; more than one issue per field; routing ignoring the flag; the check overwriting the environment instead of only flagging; the dropped-date branch disabled; a recorded date conflict flagged anyway; flagging even when no date is null. Two of those initially survived and exposed vacuous tests (the "conflict already recorded" test used an already-null value; no test covered a correction that also names the superseded date); both were fixed and re-run. One real defect was found by the tests while writing them: the "describes the old value" guard for corrections looked back a fixed 30 characters, so "previous environment **was** production, the right one is staging" skipped the correct assertion; it now looks only within the assertion's own clause.

**Live observations (provider responses, not part of the automated tests; full detail in `accuracy.md`):**
- Probe set of 11 fresh messages: 119/121 fields and 10/11 routing with the earlier prompt. The model applied all six corrections correctly and left the unlabelled change unresolved, but recorded no mismatch issue in 3 of 3 mismatch cases and left several nulls unexplained, which `finalize` now covers.
- Two extraction errors from that run were repaired in the **prompt** (revision 4): `system` = "The Beacon" (IT-202) and `team` = null for a compact "Sam Ortiz, Platform:" introduction (IT-205). Sealed set, first and only single run: 7/10 messages fully correct, 106/110 fields, 8/10 routing; over three further samples the final system was fully correct in 19/30 versus 13/30 for the previous system, with routing 22/30 versus 13/30. - The prompt rules that live probing showed the model needs are guarded by tests that check the prompt text (they cannot check that the model obeys them; the live probes, the dev set and the held-out sets do that).

**Limits of the correction check:** it only flags, never rewrites, and only for what it can read unambiguously (environment, permission, request ID, and "did the extraction use any date the correction names"). It cannot verify a corrected manager, requester, team or free text, and it does not recognise corrections that are not labelled "Correction". The detection is regex-based and tuned on the supplied wording plus the 11 probe messages; unusual phrasing can be missed (no flag) or, rarely, flagged wrongly (a person looks at a request that was fine). Withdrawal detection relies on the model's `kind`; a withdrawal the model labels `new` is routed as a new request.

## Credential redaction (`tests/test_redaction.py`, plus an end-to-end test in `tests/test_parallel.py`)
All keys in the tests are made up (assembled from pieces so no secret-shaped literal is in the source). Provider results are **mocked**; the end-to-end test uses a real `python -m intake` process and real HTTP.

| Surface | Assertion |
|---|---|
| `redact()` | removes the exact configured key even when it has no recognisable shape (a gateway key `gw_live_…`); removes `sk-…` and `sk-proj-…`, a truncated echo of a key, the provider's masked echo (`sk-proj-****abcd`, including the visible tail), `Authorization:` values of any scheme (Bearer, Basic) in header, dict and JSON forms, a bare `Bearer` token, `user:password@` in URLs, `api_key=` / `"api-key":` / `client_secret=` parameters; leaves ordinary log text untouched (including `max_output_tokens=1500`, "Unexpected token", `OPENAI_API_KEY is not set`) and is idempotent; a configured value of 6 or fewer characters is not substituted everywhere (it would mangle ordinary words), shape patterns still apply |
| Logs | messages and arguments are redacted; **tracebacks and chained exceptions are redacted** (`log.exception` — this leaked before the fix); the pipeline logs nothing secret when an unexpected error occurs |
| Stored errors and exports | a provider error that echoes the key (SDK status error, or an arbitrary exception) leaves no key in the stored error, in any exported file (`extractions.jsonl`, `queue.json`, `history.jsonl`) or in the SQLite file; every stored error passes through one redacting choke point (`pipeline._error`) whatever its origin |
| Uncaught exceptions | a crash at the CLI prints a redacted traceback and exits 1; argument errors (exit 2) and Ctrl-C are not swallowed |
| `request-evidence.json` | contains no key and shows `Bearer [REDACTED …]`; the document passes redaction unchanged (so the guard cannot misfire on it); **writing is refused, and nothing is written, if anything credential-shaped would appear in it**; it embeds the real prompt |
| The repository | no secret-shaped string (`sk-…` of 20+ characters) in any **file git tracks** (what "committed" means), tests included — gitignored local files are deliberately not part of this scan (the session capture is full of this suite's made-up keys); separately, if a real `OPENAI_API_KEY` is set in the environment running the tests, it must appear in **no file under the repository at all, tracked or not, binary included** (so a key landing in the local store or the submitted session capture would be caught; skipped when no key is set); a one-off scan of **all 40 commits** found neither the real key nor any key-shaped string, and the session capture contains only the made-up test keys and no fragment of the real one. Mutation-checked: a secret-shaped string planted in a tracked file fails the scan; the same string in an ignored file does not; a made-up configured key planted in an ignored file fails the stricter scan |
| End to end (8 runs) | a real intake process whose provider reflects the credential in its error response — as `Authorization: Bearer <key>` and as the bare key quoted in prose, for an `sk-` key and a non-`sk-` gateway key, with a non-retryable (400) and a retried (500) failure, at `INTAKE_LOG_LEVEL=DEBUG`: the key is confirmed to have been **sent** (the provider saw it), and is absent from the process log, the SQLite file including its write-ahead log, every exported file, and the output of `queue --json`, `history`, `status`, `export` and `check-export`; failures are still reported usefully (`retry-extraction`, the retry command, `[REDACTED]` where the key was) |

**Gaps this work found and fixed.** (1) Tracebacks printed by `log.exception` bypassed the redaction filter (it only rewrote the log message), so an exception message containing the key reached the log in clear text. (2) Stored error messages were redacted only where the provider text was formatted, not at the point they are stored. (3) The patterns missed the provider's masked echo, Basic/other `Authorization` values, `user:pass@` URLs and `api_key=` parameters. (4) A crash at the CLI printed Python's raw traceback. (5) `request-evidence.json` had no check at all. The new tests failed on the previous code in exactly these places (11 failures) before the fixes. One fix needed a second attempt: the first version of the Authorization pattern backtracked and treated the word "Bearer" in the deliberate `Bearer [REDACTED …]` header as a secret, which made the new evidence guard refuse the legitimate file; the lookahead now covers the scheme word.

**Mutation checks (each caught by a named test, run against temp directories, real store and deliverables verified untouched):** exact-key replacement disabled; secret-shape patterns disabled; formatter passthrough (tracebacks); log filter not redacting messages; stored errors not redacted at the choke point; provider error text not redacted anywhere; uncaught exception printed raw; evidence guard removed; the Authorization pattern removed. A further check showed the end-to-end test could initially not tell whether the exact-key layer worked (the echoed header was always caught by the shape patterns); the bare-echo style was added so that disabling that layer alone now fails exactly the two gateway-key bare-echo runs.

**Limits.** Redaction is a safety net keyed on the configured key and on common shapes: a secret of an unrecognisable shape that is *not* the configured key (for example a different token a proxy invents) would not be caught. Exported extraction text is deliberately not redacted (it must remain the requester's exact words), so a secret a requester pastes into a message is stored as written. The OpenAI SDK's and `httpx`'s own debug logging is outside this protection. Process memory, core dumps and the environment of the process are outside it too. The key is read from the environment, so it does not appear in `ps` arguments, but anyone who can read the process environment can see it.

## Operating assumptions and limits
- **Workload:** designed for 200–400 messages/day, bursts of ~2,000. Each document is one model call. `INTAKE_WORKERS` (default 4) bounds concurrency. A slow message occupies one worker for at most `INTAKE_TIMEOUT_S` × `INTAKE_MAX_ATTEMPTS` plus backoff (default ≈ 4 min worst case), never the whole run. Rate limits are handled by one throttle shared by all workers: a 429 (honouring `Retry-After`, capped at 60 s) pauses every worker and widens call spacing, which decays after successes; `INTAKE_MIN_INTERVAL_S` sets a permanent floor if the shared model quota needs one. Elapsed time for a burst is about `documents × latency ÷ workers`: 2,000 messages at 1.5 s per call is ~12 minutes with 4 workers, ~6 with 8 — **an estimate; the live provider was only exercised with 21 documents and never driven into a real 429**, so the throttle is verified against simulated 429s only. Raise workers only with the quota owner's agreement, because the model is shared with other internal tools.
- **Outage:** after `INTAKE_BREAKER_THRESHOLD` (default 10) consecutive documents fail with a provider-level error (429, timeout, connection, 5xx, auth) the run stops calling the provider and records every remaining document as an error (`provider-down-skipped`) with its retry command, so a 2,000-message intake ends in minutes with every document accounted for. Per-message problems (refusal, malformed output) do not trip it. Breaker state is per run; `python -m intake retry` starts fresh.
- **Shared operation:** one SQLite file in WAL mode with an at-most-one-pending-attempt-per-document unique index; claims use `BEGIN IMMEDIATE`, and the "is this already done?" and "is the state what I decided on?" checks run inside the same transaction as the claim. This suits operators on **one host (or one machine's filesystem) sharing the database and output directory**; it was verified there with real parallel processes (see "Real parallel operators" above). Operators in different offices on separate machines need a shared database service (e.g. Postgres) and a shared lock for exports — **not implemented, and not tested**: SQLite WAL and `flock` are unreliable on network filesystems, so do not point `INTAKE_DB` at an NFS/SMB share.
- **Concurrent exports and consistent reads:** each export takes an exclusive `flock` on `<out dir>/.export.lock`, takes its snapshot *inside* the lock, then publishes `history.jsonl`, `extractions.jsonl` and finally `queue.json`, each atomically (temp + rename). A slow exporter therefore cannot overwrite newer work with an older snapshot. **Two separate files cannot be replaced in one atomic operation**, so a reader that opens them without coordination can still straddle a publish and hold an older `queue.json` with newer `extractions.jsonl` (the window is microseconds wide in normal runs; the test stretches it to 25 ms and a naive reader hits it every time). Consistency is therefore guaranteed on the read side: every line of `extractions.jsonl` and `queue.json` carry the same content-derived `snapshot_id`, and `report.read_consistent()` / `python -m intake check-export` (a) hold a *shared* lock on `.export.lock`, which excludes any export for the duration of the read, and (b) verify the ids and the per-document `attempt_id` / `source_sha256` agree, retrying and finally raising rather than returning a mixed pair. Anything that reads the two files directly (`cat`, a script, a spreadsheet import) is not protected by the lock: it must compare `snapshot_id` itself, or take `flock -s <out dir>/.export.lock` around both reads. Files committed to git are static and always a matching pair (checked with `check-export`). `flock` does not exist on Windows; there writers are not serialised and readers rely on the verify-and-retry layer only.
- **Interruption:** Ctrl-C stops new documents from starting, keeps everything already committed, and releases this process's in-flight claims so a rerun does not wait; those documents appear under `pending` with a retry note. After a hard kill (no chance to release) claims remain `pending` and are taken over after `INTAKE_LEASE_S` (600 s) or by `python -m intake retry <doc>` once the lease has expired. Documents that were never started have no record yet — the way to find them is to re-run `intake` on the same export directory, which skips finished work. A crash mid-call may repeat that one model call.
- **Refresh limits:** the policy version hashes the whole text of `office-policy.md` and `routing.py`, so even a comment or whitespace edit marks every result stale (cheap: a re-route, no model call). Settings outside the fingerprint (`OPENAI_BASE_URL`, i.e. a different gateway serving the same model ID) are not detected as changes. `refresh` re-reads each source from the path recorded at intake; if a file has moved it records a visible `unreadable` error and keeps the earlier result. Staleness is judged per document against the configuration of the process that runs the command, so operators must run with the same environment variables.
- **Not covered:** operators on different machines, more than four simultaneous operator processes, multi-process runs at the 2,000-document scale (the scale test is single-process; the parallel tests use 12–60 documents), very large exports, provider outage longer than the retry window beyond marking documents `error`, prompt-injection variants beyond IT-006 and the regex backstop (which catches only known phrasings), non-English messages, and any model other than `gpt-4.1-mini`.
- Approvals are never made by the application; every successful record waits for human review.
